================================================================================
THE TASK
================================================================================

The kernel names classes and styles none of them. Ship the stylesheet.

A page served by a real deploy today is **blank and white**. Not broken — the
kernel booted, the parts loaded, the DOM is correct — and there is not one CSS
rule anywhere, so nothing has a background, a height, or a border.

    kernel artifact files: index.js        ← that is the whole artifact
    find src -name '*.css'                 ← nothing

================================================================================
WHAT THE DESIGN ALREADY SAYS
================================================================================

`spec/serving.md` §3, and it is not a new decision:

    **The kernel owns the rules. The site owns the values.**

    .window { background: var(--surface); color: var(--ink) }   ← kernel, one stylesheet

That is what lets two instances of one Application sit side by side under
different themes with a single stylesheet between them: custom properties
inherit, so setting them again on a window host re-themes everything inside it.
No shadow DOM, no build-time scoping, nothing to collide — because there is only
one set of rules.

The rules were never written. They lived inline in a hand-written `index.html`
in a site repository, and when the cdn started generating pages that file went
away and nothing replaced it. `spec/serving.md` §5 lists the open question —
*whether the window frame ships with the kernel at all* — and the blank page is
that question being answered by default rather than on purpose.

================================================================================
WHAT THE KERNEL ACTUALLY EMITS
================================================================================

Grep found these, and they are the whole surface:

    window  titlebar  buttons  grip  label  content  mesh-notifications

plus the eleven component primitives in `src/render/component.ts`, which are
rendered as real tags with their component name as… go and look. `tag()` is
where a name becomes an element, and it is the only place below the renderer
that knows an element exists.

Read `src/window/page.ts`, `src/window/frame.ts` (or wherever `defaultFrame`
lives) and `src/kernel/start.ts` before writing a rule. Style what the kernel
emits, not what you would emit.

================================================================================
WHAT IT HAS TO GET RIGHT
================================================================================

1. **Every colour is a token with a fallback.** `var(--surface, #161b22)`. A
   part or a page that supplies no theme must still be legible — a stylesheet
   that renders nothing without a theme has moved the blank page rather than
   fixed it. Name the tokens you introduce; a site sets them and needs to know
   what they are called.

2. **The window host needs a height.** This is the specific reason a window can
   be "open" and invisible: the manager measures its host, and a host that is
   auto-height is zero tall, so every window clamps to nothing. That failure
   looks exactly like a window that never opened.

3. **`position` belongs to whoever writes `left`.** The kernel already writes
   window geometry as inline styles, so the stylesheet must not fight it — see
   the existing comment about *whoever writes `left` owns `position`*.

4. **It has to reach the artifact.** A `.css` file that nothing imports is not
   in the bundle. esbuild emits CSS beside the JS when the entry imports it, and
   the cdn links whatever stylesheets the kernel artifact contains — so check
   the built artifact has two files rather than one, and say how you checked.

5. **Do not style the component primitives into a design system.** `Stack`,
   `Card`, `Button` need enough that a view is legible — spacing, a border, a
   readable button — and no more. A design system ships separately; this is the
   floor, not the house.

================================================================================
HOW TO CHECK IT
================================================================================

There is a browser test harness in this repository as of 0.5.0 —
`mountPart` in `src/testing/`, and `npm run test:browser` runs it against real
Chrome. A test that mounts a part and asserts a window has a non-zero height
would have caught this and does not exist.

`npm test` (290) and `npm run test:browser` (29) must both stay green.
