THE TASK
================================================================================

**A stale client is a dead end.** It detects the drift correctly and then every
call fails with the word "stale" forever, with no way back except a human
rebuilding and redeploying that part. This was reported from a live console:
*"Could not read live status (stale): stale / Could not read the fleet (stale):
stale"* — and the person reading it cannot tell what moved or what to do.

`GET /api/_describe` serves the current shapes, and `fetchApiSpec` can already
fetch it. A stale client is exactly the client that should.

**A `stale` error must carry what actually differs**: which call keys moved, and
in what way. `exposureDifference` in mesh-serve computes precisely that shape —
read it for the vocabulary, do not import it, that is a different package.

**Decide and justify: report, or recover automatically.** I lean **report**. A
client whose *types* were generated against the old shapes cannot safely start
using new ones just because it fetched them, and silently retrying against a
changed API is how a wrong answer looks like a working one. But an error that
names the three calls that changed is worth enormously more than one carrying
the word "stale" five times. If you disagree, argue it in your plan and pick one.

**Do not send `x-exposure-shape` on the `_describe` request.** The server answers
409 EXPOSURE_MISMATCH when it differs, which is a recovery deadlock for a
discovery endpoint — the descriptor is what a stale client fetches in order to
stop being stale. It is unreachable today only because the client never sends
that header. Fixing the server side is FLYBYME/surfdns#48 and is not yours.

Do not weaken or remove the staleness check itself. It caught a real drift today
and the drift was real; the problem is what happens next.
