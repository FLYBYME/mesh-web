--- 1. Fetch the exposure descriptor at run time ---------------------------

`GET /api/_describe` exists and is gated `public` (mesh-serve, merged). It
carries `input`, `output`, `gate`, `destructive`, `errors` and `stream` per call,
with `ETag`/`304`. **Nothing fetches it.**

A client should be able to obtain an `ApiSpec` from a live site, not only from a
build-time generated file. Keep `net/api.ts`'s rules: structural types, never
`z.infer` across a package boundary, and a generated file states the shapes it
means.

Carry **`shapeHash`, never the exposure hash** — `net/client.ts:154` documents
the distinction and getting it backwards is a bug that was already fixed once.

**Do not send `x-exposure-shape` on this request.** The server answers 409
EXPOSURE_MISMATCH when it differs, which is a recovery deadlock for a discovery
endpoint — the descriptor is exactly what a stale client fetches to stop being
stale. It is unreachable today only because the client never sends that header.
If you think the server should change, open an issue on mesh-serve and link it;
do not change it from here and do not work around it by sending the header.

--- 2. `ctrl+alt+q`: a full-screen log viewer ------------------------------

Asked for twice and still unbuilt. `kernel/broker.ts:418`'s `makeLog` pushes
into `services.logs`; `services.logs.push(...)` also appears in `start.ts` at
lines 185, 423, 437, 450, 518 and in `kernel.ts:163`.

**Six writers. No reader.** Every `cx.log.*` from every part and every kernel
warning — manifest conflicts, mount failures, a part that failed to start — is
collected perfectly and shown nowhere. Reported as *"i believe there are logs but
i never see them."*

Requirements that decide the design:

  * **It must work on a site with no chrome.** `window/page.ts:148` — chrome is
    optional and a site without it mounts the window layer at the root. This is a
    kernel-level affordance, which is exactly why it is a keybinding and not a
    button somebody's shell has to provide.
  * **Check `BROWSER_TAB_RESERVED`** in `kernel/start.ts`. The existing default
    bindings are chosen against it and this one needs the same treatment: a
    binding that fires *and* triggers the browser's own action is worse than none.
  * **The array is unbounded and only grows.** That is a leak in a page left open
    for a day. Decide the bound, say what happens when it is reached, and make
    sure the viewer shows that it happened rather than quietly dropping.
  * A log record carries `level`, `source`, `message` and sometimes `data`. Being
    able to see which part emitted a line is most of the value; filtering by
    source and level is worth more than pretty formatting.

--- 3. A confirmation capability, so `destructive` can have a reader --------

`destructive: true` is declared on every contract that writes, travels in the
descriptor, now reaches the browser — **and nothing reads it.**

There is no way to ask a person "is this ok?" and wait for an answer. `Dialog` is
a primitive that renders a `<dialog>`; `notifications` is a one-way signal array.
Neither is a decision.

Build the capability: a contribution declares it, the kernel provides it, a call
asks and awaits an answer. Two things it must get right:

  * **Declared like every other capability**, so a site can read its manifest and
    see which parts are able to interrupt the user.
  * **A caller must not be able to pretend the user answered.** If the resolution
    can be forged by the asking code, the capability is decoration.

**Do not wire it to `destructive` automatically in this PR.** Build the
capability and name the intended consumer; making every destructive call prompt
is a product decision that deserves to be made in daylight, not to arrive as a
side effect.
