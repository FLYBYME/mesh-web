================================================================================
THE TASK
================================================================================

A collection must not fire a request that is certain to fail for want of a
session, and must load itself when a session arrives.

Reported as: *"when i login it needs to be notified if it needs auth and then
update."* Today signing in leaves every collection sitting on the 401 it got
before there was a session, and the page looks broken until it is reloaded by
hand.

--- What is already true ----------------------------------------------------

`AuthApi.session` is a `Signal<Session | null>` (see `mesh-core/src/auth/
contract.ts`). The information is there and it is reactive. Nothing subscribes
to it.

`AUTH` is already a provider token exported from this package.

--- 1. A collection reacts to the session ------------------------------------

When the session changes from absent to present, a collection that failed for
want of one reloads. When it changes to absent, it must not keep showing another
person's rows.

Signing out and signing back in as somebody else is the case that decides the
design: a collection holding rows from the previous session is a data leak in
the most literal sense, and it will look exactly like a caching bug.

--- 2. An Application can say it needs a session -----------------------------

Make it declarable and therefore visible in the manifest — the point of a
manifest is that a contribution's requirements can be read without reading its
source. Today `catalog` needs a session absolutely and its `NEEDS` line does not
mention it.

Design this yourself and justify it in your plan. The obvious shape is that a
contribution `consumes(AUTH)`, but consuming is not the same statement as
*requiring*, and an Application that is merely improved by a session is a real
case (a public blog with an edit button). Say which you are building and why.

--- 3. Deliberately NOT in this PR -------------------------------------------

**A collection knowing on its own whether a call needs a session.** That needs
the gate as runtime data, which is FLYBYME/surfdns#39, in mesh-serve, being done
in parallel. Do not invent a second source of truth for the gate and do not
hardcode a list of which calls need auth — when #39 lands, this should be able
to consult it with a small change, so leave the seam where it fits.

Until then a collection may react to *failure* (a 401 it actually received) and
to the session signal. It may not guess in advance.

Read `../mesh-web/spec/schema-driven-ui.md` §1 for what #39 will provide, so the
seam you leave is the right shape. It is short.

--- Constraints that decide which fixes are acceptable ----------------------

  * **This is a kernel change, so it is a PATCH.** At 0.x a minor invalidates
    every part: `^0.15` excludes `0.16.0`. The kernel is at 0.15.2. A fix is a
    patch. This has been got wrong before.
  * **Bump BOTH `package.json` and `mesh.json`.** They have drifted two minors
    apart before because a dispatch bumped one.
  * Do not make the window layer, chrome, or any Extension a dependency of the
    models capability. `page.ts:148` shows chrome is optional and must stay so.
  * A part cannot be assumed to exist. A site with no auth Extension at all must
    still boot and must still load public collections.
