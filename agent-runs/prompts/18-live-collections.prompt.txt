--- 1. A collection knows whether it may fire, and notices when that changes ---

Three defects that compound. **Fixing any one alone makes things worse**, so
plan them together.

  a. `shouldFetch()` declines only *after* being refused once, so every
     collection fires blind on load and the person sees errors before doing
     anything. `ApiCall.gate` is runtime data now — ask it.

  b. The session effect reads `getSessionSignal()`, and **returns early having
     read nothing reactive** when auth has not published the session yet. An
     effect with no dependencies never runs again: the collection is deaf to
     sign-in for the life of the page. This is the *"login then click every app
     and click refresh"* symptom and item (a) does not touch it.

  c. Refetch on sign-in is gated on `failedForAuth`. A collection correctly
     *held back* by (a) never failed, so it would never load either — nothing
     errors and nothing appears, which is worse than today.

**A session arriving must load every collection with no data**, however it came
to have none.

Keep what is already right: rows clear on sign-out, and clear on a user switch
before refetching. A collection holding the previous person's rows is a data
leak, and those tests exist for a reason.

--- 2. Live collections, so no screen needs a Refresh button ----------------

Every piece exists and nothing joins them:

  * `defineCrud` generates `created` / `updated` / `deleted` per collection
  * a site declares which events it streams and the gate on each
  * the API streams them to the browser over `/events`
  * delivery narrows each event to the subscriber's scope, and an event that
    cannot be scoped reaches nobody

A collection subscribes to its own domain's events and applies them: insert on
created, replace on updated, drop on deleted.

Three things that decide whether this is trustworthy:

  * **Reconnect must resync, not assume the gap was empty.** The mesh delivers
    at-most-once; a dropped event is silent and a screen that quietly diverges
    from the database is worse than one that is stale and says so.
  * **An event for a row this collection's query excludes must not be inserted.**
    A `find` with a query is a *view*, not the whole collection.
  * **Do not double-apply.** A write made by this page will come back as an
    event; the row must not appear twice.

If the site does not stream a given collection's events, the collection must
still work — it simply is not live. Say so in `status`, do not fail.
