--------------------------------------------------------------------------------
WHAT IS TRUE RIGHT NOW — verify each before changing it

- `src/window/page.ts:36` reads `import { render, type RenderOptions } from
  '../render/dom.js';`. **That is the hard import.** There is no renderer
  interface, no injection point, and nothing for a second renderer to implement.
  The one true driver in the system is a static import.
- `PRIMITIVES` is a `const` array in `src/render/component.ts`, registered once
  at `src/kernel/start.ts:265`. `PrimitiveDefinition` is now correctly documented
  as internal to the DOM driver — it stays that way.
- `StorageProvider` **is** a proper driver and is the only one: an ops table,
  several implementations, bound per hive, with `RESOLUTION_ORDER` as the search
  path. It is a VFS borrowed from NT deliberately, and `src/kernel/hives.ts` says
  so. **Read it. It is the shape to copy.**
- The kernel already has an object registry with tokens
  (`src/contribution/provider.ts`) and a configuration manager with hives. What
  it lacks is the I/O manager: one place a driver registers, one interface per
  subsystem, resolved at load.

--------------------------------------------------------------------------------
THE TASK

Define the interface a renderer implements. Register the DOM renderer as the
default. Make `window/page.ts` — and anything else that imports `render`
directly, check `shell.ts` and `host.ts` — resolve it instead.

**Use the mechanism that already exists.** If the object registry with tokens can
carry this, use it. Do not invent a second registration mechanism beside
`StorageProvider`; if anything, this is the moment those two start looking like
one thing, and saying so in the report is worth more than a clever new file.

Keep the seam narrow. The interface is what a renderer must implement, and
`PrimitiveDefinition` is **not** part of it — a terminal or canvas renderer would
not have a table of DOM elements, it would have whatever its platform needs.
Getting this boundary wrong is the whole risk in this dispatch: an interface that
mentions `Element` anywhere has not separated anything.

--------------------------------------------------------------------------------
THE SWAP TEST IS THE DELIVERABLE

**A renderer interface with one implementation has not been shown to be an
interface.** Write a test that:

1. registers a second renderer that touches **no `document`** — one that records
   the description nodes it was asked to realise, in memory;
2. mounts a part against it;
3. asserts the part rendered correctly, **with no part changing**.

If you cannot write that test, the seam is in the wrong place. **Move the seam;
do not weaken the test.** A test that asserts a token was registered proves the
registry works, not that the renderer is swappable.
